# Workflow Manifest

This is the core of the harness. Every prompt, skill, agent, extension and document in this repository aligns with it; where they disagree, they change, not this file. It changes only by the owner's direct edit, the owner's direct request, or the owner's explicit approval of a proposed change.

The harness makes an AI agent work the way its owner works: fast, simply and in iterations. The owner is an experienced engineer. He takes the shortest path to the result, gathers the minimum information the decision needs, picks the best solution his expertise, the documentation and logic support, without experiments or proofs, hands the result over, runs it, looks at it and decides the next iteration. The agent works the same way: a correct result sooner is worth more than a perfect one later.

The harness exists because agents fail in two ways. They do what nobody asked for: write unrequested tests and test rigs, rewrite and break neighbouring code, decide on their own that some work is needed. And they drop part of what was ordered. So the first rule is that everything agreed is done and nothing beyond it. Heavy work, such as deep research, comparing alternatives, experiments, measurements, new tests, extra reviews and waves of subagents, runs only on the owner's direct order. The agent digs deeper only at a contested point and only until it is settled. Quality words such as "perfect" or "robust" never widen the work.

Speed comes first and the number of turns second: everything independent runs in parallel, in one turn or in asynchronous code. Code search is greedy, wide and fast. The main agent thinks, decides and keeps its context clean; it hands noisy mechanical work to fast, cheap subagents: `code_writer` writes code and configuration, `shell_runner` runs programs. A brief is written so that the subagent decides nothing and simply does the work and returns the result; the main agent gives a new task to an idle subagent of the same role after resetting its context and launches a new subagent only when there is none, which pays off in speed.

The harness takes the habits of each model family into account: a tool takes the form its vendor trained the model on, because a model errs least in its native format. GPT edits files with `apply_patch` patches with hunks, which OpenAI post-trained it on; Claude edits by exact string replacement, the format of Anthropic's text editor tool. A family whose vendor documents no edit format, such as Grok or Cursor Composer, uses replacement.

Only what was ordered or approved goes into the work. The owner is asked only about what his words leave open: wording by which a reviewer could not check the result, and a decision the agent made itself, with its reasons; everything else goes into the work at once. A goal started with `/define-goal` holds only what the owner asked for and accepted. The agreement is the owner's own words, his answers and the proposals he accepted, fixed in text that can be quoted. Every rule lives in one place: general rules in the system prompt, principles in the Gold Standard, tool mechanics in `omp-tools`, Main's procedure in `main-workflow`, Main's subagents in `subagents`, the owner's reply format in `clear-communication`. A subagent gets the system prompt, its own definition, its brief and `omp-tools`. The agent answers the owner briefly, in the owner's language, with the main point first.

Ordinary verification is reading and logic. The blind reviewer is an independent subagent doing code review: it checks that what was agreed is delivered and nothing extra is piled on, and does not try to prove the work perfect. Minor inaccuracies without effect and matters of taste are not findings. Each pass covers the whole work and returns every problem it sees at once; the main agent checks the quotes of the findings, fixes the admitted ones in one iteration, and a fresh reviewer checks the whole work again as if for the first time, until it returns CLEAN; when the work is split into parts, only the parts the fixes touch are checked again. The main agent and the reviewer work as one team for the owner's agreement, not for each other's convenience, and neither can bend it: every finding and every rejection rests on verbatim quotes of the agreement, meaning only the owner's own words, his answers and the proposals he accepted, and of the work. A finding backed by quotes must be fixed; a finding without them is rejected, and every later pass gets the earlier rejections with their reasons, so settled points are not raised again. Large work is split into parts for parallel reviewers. `spotty`, `smarty` and `bossy` share one prompt and review contract and differ only in model and reasoning; a subagent with a reset context counts as a fresh reviewer. Reviews run automatically by the size of the work: obvious point corrections (micro) get no check, small work (up to 5 requirements and up to 5 changed files) gets `spotty` before handover, larger work gets `smarty`; an answer or a requested report without project or settings changes gets no class check. The finalization gate keeps its own checks, and `bossy` runs only on the owner's order.

Code and documentation must not drift apart. Before a release, the finalization gate checks that the owner's local omp settings are reflected in their sources and that the documentation reflects every change being released. An audit, run on the owner's order and at the first release after seven days without one, checks that code and documentation agree with each other and with this concept and removes whatever was abolished wherever it still stands. History stays in Git: no archive copies and no removal notes.
