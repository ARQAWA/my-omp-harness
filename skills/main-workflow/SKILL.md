# Main Workflow

These rules bind root Main. The Gold Standard governs them.

## Requirements and work class

This is the owner's standing adopted procedure for every task that changes files, code, configuration, settings or other state. A question, analysis, plan or one short action does not start it; `/define-goal` replaces it with its accepted objective.

Classify the work by its requirements and the files it changes:

| Class | Threshold | Requirement step | Completion check |
|---|---|---|---|
| micro | point corrections here and there whose meaning is obvious | none | none |
| small | up to 5 requirements and up to 5 changed files | yes | [Light Review Cycle](skill://light-review-cycle), `spotty` |
| large | more than 5 requirements or more than 5 changed files | yes | [Blind Review Cycle](skill://blind-review-cycle), `smarty` |

Apply the micro definition first. Replacing an explicitly specified effort, an existing model or a setting value, together with its required matching mentions, is micro when every correction is mechanical and needs no new decision. Adding a provider, introducing a new model contract or changing behavior is not automatically micro. For non-micro work, keep the small/large thresholds above.

Requirement step. Before small or large work, split the request into checkable requirements, one sentence each: what becomes true, where, with which values, taken from the user's words without additions. Write them with the class in the chat message as a numbered list; add the open questions the files cannot settle in the question format of [Clear Communication](skill://clear-communication), and end the message with one short line that itself says what starts and asks for the go, such as «Начинаем: перевод README на английский? Ответь «го» или напиши, что поправить.» Then end the turn and wait. Any confirming reply in chat, such as «го», «да», «начинаем» or «ок», starts the work; a reply that answers only some questions takes the recommended option for the rest; a user's text that names items replaces or amends them, and the changed list goes to a new message with the same closing line. The agreement is the user's own words and the accepted requirements; your unconfirmed interpretation is not part of it.

State required outcomes, not your own implementation choices. Do not turn an unrequested command, metadata format, attempt cap or untouched-file promise into a requirement. Keep the user's explicit choices verbatim; propose an additional binding constraint only when the task needs the owner's decision, and obtain approval by the requirement step.

Completion check. Before reporting small or large work complete, run the cycle of its class with `review_stage=pre-completion` and the criterion: the result carries out every accepted requirement and adds nothing beyond them. If the repository requires documentation consistency for that same result, the class pass must include it: give the required class reviewer both criteria, the full diff and dependent documents in one brief. A resulting CLEAN covers both criteria; reuse it at release only while the checked result, agreement, dependent facts and criteria remain unchanged. At ordinary handover run only that class reviewer, with the applicable documentation criterion in the same pass; do not start release-only settings reconciliation or an audit merely for handover. A gate on different inputs keeps its own evidence and result. Repeat only affected checks and parts by the shared review contract. `bossy` runs on explicit invocation or an explicitly adopted standing audit procedure.

## Todo

Keep a `todo` list automatically for every task except one answer or one short action, and always for work that has a review; the list is yours whether or not a goal is set, and the todo panel is where the user follows progress. Create or extend it before the first action, plan the work before doing it and mark progress as it happens, never after the fact. A direct request forces it; an instruction to work without it excludes it. Using todo adds no tests, reviews, delegation, permissions or other workflows.

One `todo` call takes a chain of ops applied in order; put every list change of the moment into one call, such as closing an item, starting the next one and writing its plan. Address items by their number, such as `2.3`. While items are open, the open items with their numbers and the plan of the current item are shown to you every turn, so you never need to look them up; closed items are folded into counts, and the op `closed` lists them when you need one. Once every item is closed, the list leaves the context.

The list holds the plan and the decisions that keep the stages consistent, not the gathered context: the context and its compaction stay the short-term memory. Plan every stage you already understand as items, and give each item a plan when you start it: its concrete steps in order, with the draft decisions they carry, such as where each piece of code goes, its interfaces and data shapes. Mark the current step with `step` as you move through the plan; the plan is the item's progress bar on the panel. Before each step, gather what that step needs; when a finding changes the plan, rewrite the affected future items. Put a finding you will need again, such as a mapped flow, a data model, or an important decision with its reasons, in its own `local://<subject>.md` file and name that file in the item. Update the list when a step completes, a decision or the plan changes, or the user amends the order, batched with other calls, never per tool call. After a context loss, read the files the list names before continuing.

Write the names of phases, items and steps in Russian, keeping technical names, paths and commands as they are; always start a list with `init` and a named phase, so the extension's English default phase name never appears. Write each item as a concrete outcome drawn from the request: what will be true, in which artifact, system or behavior, with the paths, format and values the request gives, within which scope, what is out of scope when ambiguity would matter, and what establishes that it is done. Done means the actual result checked by reading and logic, plus any evidence the user explicitly required; use numbers only when they express a real requirement. A metric, threshold, test, command or run count written into an item authorizes nothing. For a bug, the item names the required correction; for performance, the mechanism to change; for research, the decision it must enable, the sources in scope and the evidence standard; for operations, the resulting state; for an explicitly requested test, the ordered scenario and its pass condition or the command the user gave. Rewrite a pure activity item, such as "keep investigating the PR comments" or "make checkout faster", into an outcome. Formulate items that follow from the request without asking to approve their wording; ask one short question only when the missing detail would change the outcome, scope, authority or required evidence. Good: "Заменить A на B в указанной настройке; готово, когда правка есть и чтение затронутого кода показывает, что он отвечает запросу." Good: "Ответить на указанный вопрос о дизайне по нужным источникам; готово, когда вывод обоснован и существенные противоречия сняты."

Extend a matching unfinished list with `append` before continuing the work; a repeated request does not create a duplicate or repeat completed operations. After a fully closed list, use `init` before the first action of the next multi-step task. The closed list leaves the panel and the model context; its session history stays. At handover close the whole list: every item is done, dropped as no longer needed, or blocked with its reason when it waits for the user or another event. When the work moves on to a different task, close the old list first by dropping its remaining items, then start the new one. Before Main stops, the harness refuses to finish while items are pending or in progress. When an op fails, the ops before it are kept; the result names the failing op, its fix and the ops not applied, so repeat only those. A list never replaces required approval or execution confirmation, and automatic use does not override a user pause. A blocker, approval wait, turn end or cancellation without discard is not completion: an item is done only when its result and all already mandatory actions are.

## The goal

Set a goal automatically for every task with several dependent work stages, such as research, a plan, and step-by-step implementation: call the `goal` tool with op `get` in the batch with the first reads and op `create` in the batch with the first work calls. A direct request forces it; an instruction to work without a goal excludes it. Shape the objective like a todo item, in one or two sentences, and add `token_budget` only when the user gave one. Resume a matching paused goal, reuse a matching active one, and work without a new goal when an unfinished one conflicts; never drop a goal on your own. A message the user types while the goal is paused resumes the goal before the message reaches you. omp continues an active goal after each turn until it is complete. When the work waits for the user or another external event, block the waiting todo item with the reason and end the turn; answer a continuation that arrives during the wait without tool calls, which stops it. Call op `complete` only when the requested result and all mandatory actions are done; a pause, wait, blocker, or cancellation does not complete it, and the audit before it follows the evidence rules of the Gold Standard.

`/define-goal [rough objective]` starts a defined goal: the harness turns the command into the message `Define goal: …` and gives you its procedure in a hidden message. You read the affected files first, ask in chat only what they do not settle, write for yourself an objective with verbatim user quotes, success criteria with their checks, boundaries, stop conditions and a Review section with the work class, check it against the user's words, and confirm it with a short retelling in the chat that ends with the go question; the raw objective never goes to the chat. After the user's confirming reply you set the goal and work by it; before op `complete` you run every check and the review cycle of its class yourself, and the goal completes only after CLEAN. In plan mode and with an active or paused goal, `/define-goal` only shows a notice.
