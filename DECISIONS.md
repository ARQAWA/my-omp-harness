# omp-lite: decisions

Every accepted decision about the omp-lite stand, with its reason and the file that carries it. Change a decision only by editing its entry here together with the file.

## Scope

- Work only on the `lite` branch of my-omp-harness, in its worktree `my-omp-harness-worktrees/lite`; the stand home is `~/stock-bench/omp-lite-home` and loads the package from that worktree. Never modify or bench `~/.omp` or the `master` branch; reading them is fine.
- Only the functionality omp-lite already has, plus the interface transferred from the main harness. Search behaviour lives in tool descriptions and `SYSTEM.md`.
- No Gold Standard and no Workflow Manifest principles ("everything agreed and nothing beyond", "heavy work only on request", "dig deeper only at a contested point", "shortest path"): they were written against GPT-5.6 over-engineering and fight greedy search. `harness.ts` appends only the environment line to the system prompt; `skills/gold-standard` is removed.
- `SYSTEM.md` exists twice and must stay identical: `SYSTEM.md` of this branch and `omp-lite-home/.omp/agent/SYSTEM.md` (check with `cmp`).
- Tool call arguments stay as they are.
- Internal structure and its rules are in `AGENTS.md`: one folder per tool under `extensions/tools/`, the model-facing description in its `description.md`, shared code in `extensions/shared/`, no mentions of other products.

## Measurement

- Speed is wall clock only: `run.json` `(end - start) / 1000`, reported as average and median. Never derive time from tokens.
- Process startup (launch to first model request) is not a target: speeding it up is dropped (user: «Ускорять запуск не надо»). Future benches subtract it from the measured time (user: «из бенчей, из замеров убрать это время»).
- Current result accepted as final for this stage: omp-lite `expand`, first read 1000 lines, answer rules unchanged (see bench19-22).
- Fair runs: the same model and effort on every stand; omp-lite and Pi run at the same time. bench18 used `gpt-6.1-sol`, `low` (user's order); bench13-17 used `gpt-6-sol`, `medium`; the code-mode probes of `read` used `gpt-6-sol`, `low` (user's order: «Всё делай на модели GPT-6 Sol Low»).
- Runner: `~/stock-bench/bench2/bench.ts` with `BENCH_DIR`, `BENCH_RUNS=4`, `BENCH_ALL_READ_ONLY=1`, `--tests`, `--concurrency`.
- Quality: a judge scores each answer against a point checklist built from the code; a point passes at bool >= 0.5; score = 100 x passed / points.
- Reruns start only after the owner agrees on the change set.

## Tool output budgets

- `grep` and `glob`: 51 200 characters, that is 50 KB (`GREP_CHAR_BUDGET`, `GLOB_CHAR_BUDGET` in `extensions/shared/search/format.ts`), with no line cap. The first version used 15 000 and 5 000; the old harness uses 100 000 (`RESULT_MAX_CHARS`); Pi cuts bash output at 50 KB or 2000 lines. Reason: with 15 000 the first search wave could only list file names, so the model read files blind; Pi sees 20-50 KB of matching lines and picks files precisely. Only characters are capped because the model's input cost follows characters, not line count.
- No line cap anywhere: the native engine has none, and only the character budget cuts what the model sees (safety cap 100 000 matches).

## Engine

- `grep` and `glob` run on omp's Rust search engine, `grep` and `glob` from `@oh-my-pi/pi-natives`, inside the omp process (`extensions/shared/search/engine.ts`); only `.gitignore` applies. Reason: no process spawn per call, native calls run truly in parallel (8 broad searches in 83 ms).
- Differences from the ripgrep CLI: glob filters are case-sensitive; a negated glob (`!x`) is applied as a filter after the search; `multiline` does not imply dotall.
- `read` stays on `fs.readFile`: omp has no Rust file reader; its own `read` tool also uses `fs.readFile`.
- All three tools are `shared` and fully async.
- `read`: 100 000 characters (`READ_CHAR_HARD_LIMIT`). Over the limit it returns an error asking for offset and limit. The `[Use offset=N to continue.]` hint appears only on a greedy cut (no offset, no limit, more than 1000 lines).
- `read` path description says paths are relative to the workspace root; absolute paths also work.

## Parallelism

- omp runs every `shared` call of one response at the same time; an `exclusive` call waits for all earlier calls and holds back later ones (`pi-agent-core` `agent-loop.ts`).
- Every tool is `shared` (user: «Все инструменты должны быть доступны в параллели без эксклюзива, за исключениями, которые ты назовёшь сам, если обоснуешь их»). Exceptions: `eval`, because one kernel per language holds the session state; `bash` with `pty`, because it owns the terminal. `edit` with an `apply_patch` patch is `shared` too: both edit modes lock each file and refuse a busy one, so parallel patches of different files cannot collide.
- Measured: all calls of a step start before the first one ends; the gap between steps is 0.03-0.06 s. Execution is not the bottleneck.
- The cost is per model step: about 2.2 s plus 1.16 s per 100 output tokens (bench17 fit), and time to first token grows with new input. A batch saves time only when it replaces a whole step; every extra call costs about 6-8 output tokens plus its arguments.
- `SYSTEM.md` speed block: optimize for wall-clock time (each response costs about 2 s plus writing time, tools are almost free); every call that does not need another call's result goes into the same response (searches, globs, reads, writes and edits of different files, shell commands), one edit call per file; no calls whose results go unused; stop exploring once every part of the question is backed by code seen, and write the final answer once.
- `eval` is a loadable tool (see Tool set), as in the main harness, for work beyond context gathering. Its description forbids it for searching and reading code while gathering context and limits it to computation, data processing and tool calls whose output must be filtered in code. Like bash and edit, eval is a wrapper (`extensions/tools/eval/`) with the same name as omp's built-in: it calls the native eval through `ctx.invokeTool`, and its description is omp's own eval text (rendered without subagents and the wait tool, which omp-lite does not have) plus this rule. Its doc topics stay as `xd://eval/<topic>` links: `read` serves `xd://eval/<topic>` itself from omp's `getEvalDocTopics` (omp's native read serves them only for its built-in eval) and passes other internal URLs (`scheme://...`) to omp's native read, as it does images and PDF, so the docs load on demand instead of sitting in every request. Tool rules live in tool descriptions; `SYSTEM.md` keeps only rules that span all tools. Reason: in omp it is `exclusive` (`tools/eval.ts`), so inside a batch it waits for earlier calls and holds back later ones; grep, glob and read run in parallel.
- `read` description says to read every related file in one response; "read whole files rather than pieces" was removed because it contradicted the `grep` point-read rule.

## Tool set

- Base tools, in every request: `read`, `grep`, `glob`, `bash`, `edit`, `write`, `load_tools`. Loadable: `eval`, `lsp`, `ast_grep` (user: «Базовые: read, grep, glob, bash, edit, write»). Lists in `extensions/shared/toolset.ts`; `harness.ts` keeps base plus loaded tools active.
- `edit` follows the model: GPT gets `apply_patch`, other models the replace mode, both with the batching, per-file locks, partial hunk application and nearest-match errors of the main harness (user: «Если это GPT-модель, то это должен быть apply patch... надо эту прокачку всю полностью сохранить»).
- Loading goes through our own base tool `load_tools` (user chose it: «1а»): the model names loadable tools and they are active from its next response to the end of the session. Reason: omp mounts discoverable tools under `xd://` only while `read` and `write` are its built-ins (`builtInRegistryToolNames` drops a name an extension re-registers), and an extension can delegate only to the native tool of its own name, so a `write xd://` dispatcher cannot reach `eval` or `lsp`. Probes on omp 18.10.1 and 18.11.3 confirmed it. All tools therefore register as `essential`.
- Probe: asked to hash a string with eval, gpt-6-sol low called `load_tools` with `eval`, then `eval`, and returned the correct digest.
- `lsp` and `ast_grep` are wrappers (`extensions/tools/lsp/`, `extensions/tools/ast_grep/`) with our descriptions: when each beats grep, and to call it in the first wave. `load_tools` lists each loadable tool by the jobs it does exactly, and says to load in the first response. `eval` names the jobs computed over many files.
- bench24 (10 tool-shaped tasks, 1 run, stock descriptions): the model never called `load_tools`.
- bench25 (A/B, all four runs at the same time, gpt-6-sol low, 2 runs each; `OMPLITE_TOOLS=load` vs `base` in `extensions/shared/toolset.ts`). Tool tasks: load 31.5 s avg / 28.1 median, special tools used in 15 of 20 runs (16 `load_tools` calls); base 32.1 / 31.7, 18 of 20. T01-T07: load 31.4 / 27.1, no special tool used, quality 89.0; base 37.8 / 35.9, `lsp` called in all 14 runs without need, quality 90.2 (fallback judge). Decision: keep `load` (the default): the tools come in where they help and stay out of ordinary search, which they slowed by 6 s.
- Subagents are tools, one per role: `code_writer`, `shell_runner`, `codebase_explorer`, `review` (`level` light|blind|high picks the model), `custom` (user: «чтобы каждый саб-агент был как инструмент»). They run on own omp SDK sessions (`extensions/shared/subagents.ts`), not omp's `task`: one warm session per role starts with Main, a reused session gets `newSession()` before the next task, and its system prompt and tools stay the same. A call returns an id at once; the final arrives as a message, and Main waits for a running final only at its own stop, at most 25 s per stop because omp cuts a `session_stop` handler at 30 s; then Main continues with a note to end its response without tool calls until the next final. Role prompts live in `agents/*.md`; the brief and trust rules live in the tool descriptions. Commands `/lightreview`, `/blindreview`, `/highreview`.
- Models: code_writer and shell_runner Haiku 5.5 medium; review light Haiku low, blind Haiku medium, high Sonnet 5.5 low; codebase_explorer on Main's current model with Main's reasoning level capped at medium (user: "Пусть Explorer запускается на той же самой модели, что и родитель, только reasoning должен быть не выше medium"). Without Anthropic credentials (`modelRegistry.hasConfiguredAuth`), code_writer and shell_runner run on `openai-codex/gpt-6-luna` at medium (user: «если авторизация anthropic доступна, то haiku. если нет, то luna 6 medium»), and review runs on `gpt-6-sol` medium (light), `gpt-6.1-sol` low (blind), `gpt-6.1-sol` medium (high) (user: «был gpt 6 sol medium на light подписке, gpt 6.1 sol low на blind и 6.1 medium на high»).
- Subagent state lives on `globalThis`: omp loads every extension file with its own `?mtime=` import tag, so each tool got its own copy of `shared/subagents.ts`, the stop handler never saw running tasks and tools never got warm sessions. Every subagent session gets its own `agentId`; without it omp registers each one as "Main" and parallel creates fail with `Agent "Main" was replaced during session initialization`.
- code_writer rule: Main writes code itself only when the brief would be about as long as the code (a few lines, a rename); a new module, new functions, new tests or edits across several places go to code_writer. Probe: a one-variable rename was done by Main (10 s); a new module with tests went to code_writer and 40 tests passed (41 s). With the earlier wording Main wrote the module itself.
- A subagent final shows in the feed as one row in the interface style: status circle (green DONE/CLEAN, red failed, yellow otherwise), task id, then muted `· <model> <lo|md|hi|xh|mx> · <seconds>s` of the model the task actually ran on, the body under it (first line collapsed, all lines expanded) (`extensions/ui/feed/subagent-result.ts`, message `details`). Running subagents appear in the status bar's subagent count (registry `running`); the earlier separate `setStatus("subagents")` text is removed. The launch and stop texts forbid filler commands such as `pwd`, `ls` and `git status`; in bench27 they dropped from 4 to 2 per 14 runs, and a probe with two subagents ran none.
- A/B switches: `OMPLITE_EXPLORER=off` removes codebase_explorer, `OMPLITE_WARM=off` skips warm sessions.
- bench26 (explorer on vs off, at the same time, gpt-6-sol low, 2 runs each; Cursor-style description). T01-T07: on 65.2 s avg / 54.2 median, explorer in 10 of 14 runs, almost always `very thorough`, Main waiting on it; off 31.9 / 29.2. Pairwise judge (fallback `completion`, same prompt for both): on 74.4, off 83.9. Tool tasks: explorer never called, 33.0 / 31.4 vs 32.9 / 33.3. Startup with warm sessions 2.6 s, without 2.5-3.6 s: warm sessions do not delay the first request.
- Decision: the explorer description is narrowed. Main is the faster searcher and searches the question itself; an explorer takes only an extra independent area alongside Main's own first wave, `quick` by default, never the whole question. bench27 (same setup): on 25.9 / 21.0, explorer in 2 of 14 runs, quality 78.7; off 26.9 / 23.1, quality 84.2. The quality gap also shows in runs where the explorer was not called (T03: 76/84 vs 90/87), so it is within the judge's noise at 2 runs. The explorer stays with the narrow description.
- bench28 (same setup, 4 runs each): on 28.8 s avg / 23.6 median, explorer in 7 of 28 runs, quality 78.9; off 26.3 / 23.8, quality 83.5. The gap comes from 2 runs scored 6 and 12: Main wrote its answer while the explorer ran and then appended a correction after its final. The launch and stop texts now forbid a final answer while a subagent runs and ask for one complete answer after the final. bench29 (same setup): on 28.3 / 23.4, explorer in 5 of 28, quality 79.2; off 25.5 / 22.9, quality 84.5; 2 T07 runs still answered early and appended an addendum (scored 8 and 3). Without those runs both variants score the same; the explorer gives no speed or quality gain on T01-T07, and gpt-6-sol low does not reliably hold its answer for a running subagent.
- bench30 (same setup, explorer on Main's model with reasoning capped at medium): on 34.6 s avg / 25.6 median, max 174.1, explorer in 7 of 28 runs, quality 81.3; off 26.3 / 24.3, max 54.4, quality 83.4. 2 on-runs answered twice; one T07 run scored 8.
- One explorer, `codebase_explorer` (user: «я хочу сделать только одного explorer, codebase explorer пусть он будет»), modeled on Cursor's Explore subagent: a faster model running many parallel searches in its own context and returning a summary, never raw files. Main decides itself when to launch it, by the tool description taken from Cursor's Task rules: broad questions across several areas go to the explorer, one explorer per independent area in one response; needle queries, known files and quick questions are searched directly; the whole user query is never handed over just to relay the answer. The launch result tells Main to end its response without tool calls when nothing else is left, instead of polling (a stand probe showed empty `bash` calls while waiting).

## Interface

- The interface of the main harness is transferred into `extensions/ui/` (user: "перевести весь интерфейс из My OMP Harness в наш Light"): `status-bar.ts`, `feed.ts` with `feed/*` (feed rows, live action, cards, hub, to-do panel), `model-arrows.js`, `reasoning-arrows.js`, `subagent-reuse.ts`; theme `settings/titanium-arq.json` and `settings/keybindings.yml`; the stand gets the theme, keys and the status-line settings of the main harness's install step 4. The feed is renamed from its old product-named folder. Tools and agent mechanics of the main harness (`todo`, `diagram`, `results`, `rg`, its write/edit/bash, subagent model policy) are not interface and are not transferred; todo stays off, so the to-do panel stays idle.
- Warm subagent sessions are `idle` in omp's agent registry and `running` only during a task (`AgentRegistry.global().setStatus`). Reason: omp counts running registry agents in the status line, and right after start the transferred status bar showed three subagents and "Waiting for 3 subagents".

## Todo

- Off (`todo.enabled: false` in `omp-lite-home/.omp/agent/config.yml`). The built-in omp todo is `exclusive` and would act as a barrier inside a batch. The old harness todo is `shared` but depends on its feed panel. Revisit later.

## Search method

- Greedy waves, written into the `grep` description (`extensions/tools/grep/description.md`):
  - First response: several broad `grep` searches in parallel in content mode without `head_limit`, one per facet, each an alternation of every name, synonym and spelling, plus `glob` for deploy, run and entrypoint files (compose, Dockerfile, Makefile, systemd, CI, main, bin, `__main__`).
  - Next responses, one batch each: read whole the files whose matching lines show a definition, configuration or entrypoint, and the run files; read other hits only around their matching lines; continue long files from the returned line; `grep` the exact identifiers just found.
  - Stop when every part of the question has an answer backed by a file and line for the subject itself; do not follow it into neighbouring subsystems the question does not ask about.
- Reason for the read and stop rules: in bench17 omp-lite read 27 files (122 KB) per run, half of them never cited, and on T05 spent 2-4 extra steps (15-20 s) in Mongo, stats_telegram and quarantine code.
- First-wave content mode returned once the budget is 100 000; with 15 000 it truncated the wave and missed `config.rs` and `config.toml`.

## Answer rules (`SYSTEM.md`)

- Several implementations: determine from deploy and run configuration which one runs, say so, and explain for every implementation where and how it is used.
- Name the exact identifiers that answer the question: keys, constants, topics, config fields and values, with paths; describe non-running implementations briefly. Reason: on T06 the Redis key `currency:tradeoffer:cooldown:{key}` was in omp-lite's tool output in all four runs and in none of its answers.
- `textVerbosity: low` stays.

## Other settings

- omp's built-in subagents stay disabled (`task.disabledAgents`).
- Startup profile, not yet changed: `buildSessionOptions` 164 ms, `loadCachedStandardModels` 73 ms, first `rediscoverRules` 104 ms; omp-lite reaches the first request in about 1.7 s versus Pi's 0.9 s.

## Code mode of read

- `read` treats code files (py, rs, go, java, ts, js and similar) apart from text. Default variant `expand`: a range given with `offset` and `limit` grows to the enclosing blocks tree-sitter reports (`enclosingBlockBoundaries` from `@oh-my-pi/pi-natives`), at most 150 lines each way. Config, docs and other text files read as before.
- Only `expand` is in the code. The probe variants `base` (no code mode) and `map` (expand plus an outline from `summarizeCodeAsync` for code files over 200 lines read without a range) and their `OMPLITE_VARIANT` switch were removed after the probe below.
- Probe (T05-T07, 4 runs each, omp-lite only, gpt-6-sol low): base 38.2 s avg / 37.8 s median, quality 88.1; expand 37.3 / 36.2, quality 87.8; map 39.1 / 37.6, quality 87.8. map added a step and 10 calls on T05 and the model got only 1-2 outlines per run, so it saved no reading. expand was fastest with equal quality and cut T07 reads from 57 to 38 KB. Differences are within the noise of 4 runs. All variants missed the same points (T06 auth blocker delay, T07 "every prod service is Rust"), so the misses are not caused by the tools.
- Two grep tools (code and text) were rejected: questions span code and config, one grep finds both in one call, and a second tool would need a non-stock name.
